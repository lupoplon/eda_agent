# Реализация: шесть аспектов архитектуры

## 1. Диалог, состояние и ссылки на источники

В agent.py класс Agent строит StateGraph с узлами context → decide → tools. State хранит сообщения, слоты и резюме. Decision, MemoryProposal и Inspection валидируют ответы GigaChat через Pydantic. InMemorySaver хранит состояние текущего thread_id; LangGraph Store восстанавливается из SQLite между запусками.

Предметные ответы проходят grounded_answer: модель выбирает цитаты, код проверяет id источника и дословное совпадение. Неподтвержденный ответ не выводится. Числа для вопросов о таблицах считает inspect_table, а не модель.

## 2. Бюджет контекста и суммаризация

context_tokens оценивает размер рабочей истории, слотов, резюме и служебных данных. context_guard при пороге CONTEXT_TOKEN_BUDGET (по умолчанию 8000) вызывает суммаризацию порциями и возвращает RemoveMessage для старых сообщений. Правила и слоты не удаляются; при ошибке история сохраняется.

CloudGigaChat передает фактический usage каждого ответа в Agent.emit; api_totals учитывает вход, выход и повторные запросы. Оценка до отправки приблизительная, точного токенизатора провайдера здесь нет. Счетчики и уведомления показывает render_tokens в app.py.

## 3. Гибридный поиск как инструмент агента

Agent.search объединяет лексическое пересечение слов и cosine similarity эмбеддингов Cloud.ru. Выдачи сливаются RRF; точное совпадение id повышает позицию кандидата. Поиск вызывается инструментом search_rules из execute по выбранному действию, а не на каждой реплике.

В локальном режиме вместо семантических эмбеддингов используется тестовое хеширование слов. Отдельного cross-encoder нет; переупорядочивание реализовано простой эвристикой.

## 4. Метаданные, редакции и роли хранилищ

active(as_of) отбирает редакцию каждой записи по valid_from и version до поиска и обработки. Одинаковое правило может давать разные результаты на разных датах.

load_dataset и use_dataset сохраняют и выбирают неизменяемые именованные версии таблиц в SQLite. output_dir разделяет результаты по id версии; manifest фиксирует версию данных, правила и метрики шагов. Диалог и промежуточный кэш живут в RAM, правила и версии исходных данных — в SQLite, результаты — на диске.

## 5. Схема долговременной памяти

remember сохраняет id, version, kind, description, steps, valid_from, created_at, expires_at, source и source_text. Описания относятся к semantic, исполняемые правила — к procedural. MemoryProposal запрещает процедурную запись с пустыми шагами; операции проверяются типизированными моделями Dropna, Dedup, Fillna и Join.

Исходная реплика сохраняется для проверки происхождения и поиска. Срок текущей политики — до явного удаления; expires_at пока null. Автоматического истечения и отдельного профиля пользователя нет.

## 6. Управляемость, аудит и повторяемость

Таблица audit фиксирует записи и запуски. forget удаляет локальную память, версии данных, результаты и checkpoint. Обязательных к сохранению персональных данных приложение не определяет.

run исполняет только разрешенные операции pandas. Отпечатки входных таблиц, редакция и параметры правила определяют возможность повторного использования промежуточного результата. В rule_report одна строка на правило с причиной применения или пропуска; operations содержит численные основания отдельных шагов. Кэш обновляется после успешной обработки.

Журнал Agent.emit показывает обращения к модели, инструменты, метрики и ошибки; секрет маскируется. Ранжирование памяти по отдельному recency-score, полный аудит всех чтений и фоновый worker не реализованы.
